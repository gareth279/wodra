# Windows x64 releases

Wodra has exactly two update channels: Alpha for frequent testing and Stable for explicitly approved public releases. They share the Wodra app identity, per-user installation, rider data, supported protocols, and application-lifetime updater. See [windows-updater.md](windows-updater.md) for switching behavior and recovery.

## Prerequisites

The release package job uses a dedicated Windows x64 runner because its build inputs include Epic's licensed EOS SDK 1.19.2.1 and the approved client configuration. These inputs are not committed to Git or available on a standard GitHub-hosted runner. ANT+ network-key material is configured by the rider in Settings and is not a build input. The normal build/test validation uses `windows-2022`; only the package job requires the private runner. Install Godot **4.6.2 .NET** editor/export templates at `C:\Tools\Godot\Godot_v4.6.2-stable_mono_win64`, .NET SDK 10.0.204, licensed Visual Studio Build Tools with the x64 VC runtime redist, Git, and the EOS SDK at `%LOCALAPPDATA%\Wodra\EOS-SDK` (or set `EOS_SDK_ROOT`). Configure `%LOCALAPPDATA%\Wodra\eos-client.json` for that runner account using only the restricted Wodra Player client. The publisher checks the native EOS DLL, Epic's `ThirdPartyNotices` file, and Visual C++ runtime files before building. The EOS DLL imports MSVCP140 and VCRUNTIME140/140_1, so the publisher includes those app-local dependencies and the matching Microsoft redistribution notice. Microsoft allows redistribution of unmodified redist files subject to Visual Studio license terms ([Microsoft redistribution guide](https://learn.microsoft.com/en-us/cpp/windows/redistributing-visual-cpp-files)). The EOS SDK and its Samples are never copied into the release.

Create `%LOCALAPPDATA%\Wodra\eos-client.json` from `eos-client.example.json` once, using only the restricted, user-required **Wodra Player** client policy. The zero-argument release command loads this config by default; `-EosClientConfigPath` can override its path. Client credentials are extractable from a distributed application. Do not use a trusted-server credential, and do not include identity caches. See [EOS Phase 4 setup](epic-online-services-phase4.md).

## Build and verify an alpha ZIP

From the repository root:

```powershell
dotnet build wodra.sln -c Debug -m:1
dotnet build wodra.sln -c Release -m:1
dotnet run --project tests/IndoorCycling.Physics.Tests -c Release
dotnet run --project tests/Wodra.Multiplayer.Protocol.Tests -c Release

.\publish.ps1
```

Alpha versions use `MAJOR.MINOR.PATCH-alpha.N`; Stable versions use `MAJOR.MINOR.PATCH`. Tags are `v` plus the exact package version. SemVer orders `0.1.0` above all `0.1.0-alpha.N` prereleases. After Stable `0.1.0`, auto-derived Alpha development advances to `0.1.1-alpha.1`, then `.2`, and so on. Use `-Channel alpha` or `-Channel stable` for local package creation. Output retains the portable ZIP, installer, full/delta package, and channel-specific `releases.alpha.json` or `releases.stable.json` feed. Stable promotion also includes `release-provenance.json` with the source Alpha tag and commit, Stable route-manifest hash, and package artifact hashes.

The publisher serializes runs with a process mutex. It launches dotnet, Godot, and the extracted smoke test with separately captured output and errors, phase-specific logs, and timeouts; on timeout it terminates only the child process tree started by that invocation. Godot 4.6.2's managed export hook fails in this environment and has also stalled after saving the PCK. To avoid that unstable hook, the script exports a fresh PCK, stages the matching official Windows x64 .NET release template as the executable, and performs a fresh self-contained `dotnet publish` for managed files. It does not trust `.godot` cached outputs: it verifies the PCK, release template, fresh managed files, package ZIP, and extracted executable startup. `-SkipOfflineSmokeTest` skips that launch when a runtime environment cannot support it.

For local GitHub draft publishing, explicit `VPK_TOKEN` takes precedence, then explicit `GH_TOKEN`. When neither is set, `publish.ps1` reads the existing `github.com` credential from `gh auth token` without displaying or writing it. Before build/package work, it checks that credential against the GitHub repository API and confirms repository write access. The selected credential is passed only through the Velopack upload child process environment; the parent process environment is unchanged. The upload helper captures child output in memory, writes status/category only, and emits no raw response or process output to logs. A preflight error distinguishes a rejected credential, insufficient repository permission, and network/proxy connectivity; it never prints raw GitHub CLI output or credential values. The read-only credential policy tests run with `powershell -NoProfile -File tests/GitHubReleaseAuth.Tests.ps1`.

The release carries seven built-in routes: Oval to Gardens, South Dunedin Coastal, Rolling City and Valley, Signal Hill Climbing, Otago Central Rail Trail: Clyde–Alexandra (Gravel), Signal Hill – The Big Easy MTB, and Wodra XC Skills Loop (fictional). The four Dunedin road routes include route points/elevation, buildings, landmarks, street furniture, streets, terrain, and vegetation sidecars. The Gravel and Big Easy MTB packages include route points, terrain, and mapped-area vegetation. The fictional XC package contains route points, a procedural local heightfield, authored route-relative vegetation, and a versioned trail-features sidecar for jump lines, berms, and rollers. Pine Hill Test remains opt-in experimental scenery; Alpha.94 explicitly includes it as an eighth route with its route sidecars and checked runtime assets. The MTB/XC route documentation records provenance and limitations. Their scenery is baked data, so neither original source-data folders nor LINZ rasters are needed on a player machine. The route verifier recomputes each geometry fingerprint and verifies any fingerprint stored in its route file.

The archive's EOS settings file is included from the default per-user config or from the explicit `-EosClientConfigPath` override. Configuration must remain outside the Git checkout. Its secret values are never printed by the packaging or verification steps.

The archive contains the Windows export, Godot's bundled .NET runtime and managed assemblies, ANT+ runtime configuration, EOS native runtime and its app-local Microsoft CRT dependencies, client config, route packages, and third-party notices. It does not contain the EOS SDK source/Samples, debug symbols, PDBs, route-authoring inputs, identity caches, local settings, FIT files, logs, or private user profile data. Epic documents the SDK package's `Samples`, `SDK`, and `ThirdPartyNotices` directories; only the native runtime and required notice file are included in Wodra's distribution ([EOS SDK download contents](https://dev.epicgames.com/docs/epic-online-services/eos-get-started/eos-get-started-reference)).

## GitHub Releases

`.github/workflows/windows-validation.yml` runs on protected-main pushes and pull requests. It uses a Windows 2022 runner, .NET SDK 10.0.204, and the pinned Godot 4.6.2 .NET editor/export templates. The solution is built with EOS disabled (so the workflow does not need Epic's proprietary SDK), and the available console regression suites run in Release. The Godot archive SHA-256 is checked before extraction.

`.github/workflows/windows-alpha-draft.yml` is a manual, tagged release path. It first calls the standard GitHub-hosted `windows-2022` validation workflow against the selected tag (Debug and Release builds, Godot headless launch, and regression suites). Only after that succeeds does it wait for the protected release Environment and package on the private runner. It validates that the existing `vMAJOR.MINOR.PATCH-alpha.N` tag is reachable from protected `origin/main`, then creates a **draft prerelease** through Velopack. Configure GitHub Environment `alpha-release` with a required maintainer reviewer and restrict deployment to `main`. Register one isolated Windows x64 self-hosted runner with labels `self-hosted`, `Windows`, `X64`, `wodra-release`; provision Godot 4.6.2 .NET/export templates, .NET SDK 10.0.204, licensed EOS SDK 1.19.2.1, Visual Studio Build Tools/VC redist, `%LOCALAPPDATA%\Wodra\eos-client.json`, and pinned `vpk` tool restore access for that runner's service account. Never register this runner for pull-request jobs or run fork code on it.

Workflow permissions are explicit: CI and the validation job get `contents: read`; only the protected draft-release job gets `contents: write` to create a GitHub draft and upload assets. `VPK_TOKEN` is set from that job's ephemeral `GITHUB_TOKEN`, so no PAT or repository secret is required. Approving the `alpha-release` Environment is the release authorization step. No signing secret is configured until the publisher identity/certificate decision for issue #15 is made. External contributions never receive release credentials or execute on the private runner.

For Alpha, create the reviewed version tag on `main`, then run **Actions → Prepare Windows alpha draft**. It validates the tag, waits for the protected Alpha environment, and creates a draft prerelease. The owner reviews and publishes the draft as an Alpha prerelease. Local `publish.ps1 -Channel alpha` builds without uploading; draft upload requires an existing matching tag and a clean checkout at its commit.

The official Velopack Windows Setup installer uses a per-user install at `%LOCALAPPDATA%\Wodra` by default. It provides the stable launcher and `Update.exe` helper that Velopack updates through its normal lifecycle. Godot keeps the existing project name `Wodra`, so `user://` profiles, settings, ride history and other user data stay in Godot's user-data directory outside the installed application folder. Velopack uninstall removes the application and shortcuts; it does not include rider files stored in Godot's user-data path. Velopack update downloads are staged and checksum-verified by the framework; delta preparation failures fall back to the full package. A shared application-lifetime update service is presented on both the startup screen and in Settings, with a manual **Check for Updates** action, current version/channel status, and Retry after failures. Updates are applied with an explicit restart only after rides and FIT replay are complete. Feed failures and downloads do not block offline play; users can continue riding or defer installation with **Later**. See [windows-updater.md](windows-updater.md) for the PR #152 visibility regression and isolated local-package verification.

Alpha clients use the `alpha` Velopack channel and prerelease GitHub releases; Stable clients use the `stable` channel and normal GitHub releases. The updater checks public GitHub Releases anonymously; no account/token is shipped. Each channel feed is generated and uploaded by Velopack. GitHub's anonymous API limit is 60 requests/hour/IP.

## Stable promotion

`.github/workflows/windows-stable-promotion.yml` promotes an explicitly selected, published Alpha candidate. The standard Windows validation workflow runs on the exact Alpha tag. The protected private Windows runner checks that the Stable tag already exists on that same source commit, reruns the production packaging checks, and creates a draft Stable release. The workflow never creates or moves tags, and it never publishes. Configure the `stable-release` GitHub Environment with required owner/maintainer approval and main-only deployment. GitHub's final Publish release action remains a separate explicit owner decision.

The first intended Stable version is `0.1.0`, promoted from an approved `0.1.0-alpha.N` commit. `v0.1.0-alpha.94` is the current candidate but is not yet ready for owner approval based on the recorded validation state: live Strava upload and restart persistence, two-client multiplayer state/rendering, and physical BLE/ANT+ acceptance remain unverified. Resolve those acceptance items or record owner acceptance and update [release-notes/v0.1.0.md](../release-notes/v0.1.0.md) before creating the Stable tag. Pine Hill Test was added as experimental Alpha content and is explicitly excluded from the seven-route Stable manifest.

After acceptance: (1) validate the candidate tag, (2) create and push `v0.1.0` at exactly the candidate commit, (3) run **Prepare Windows Stable draft from approved Alpha** with that candidate and version, (4) approve the protected environment, (5) review draft, provenance, route manifest, ZIP, Setup, full package and hashes, and (6) explicitly publish it as a normal Stable release. Repeat with `0.1.1-alpha.N` promoted to `0.1.1` for the next Stable release. Never overwrite a release tag or package.

## Migration and recovery

Existing Alpha installs whose settings file has no update-channel field inherit their Velopack Alpha channel, preserving their feed and installation. A fresh installer uses the channel it was packaged with; the public Stable Setup starts on Stable. An explicit saved selection takes precedence. Settings switches are persisted and recheck the selected feed. The updater discovers lower versions for comparison but only offers versions that are strictly newer according to Velopack `SemanticVersion`. Existing rider data remains in Godot's per-user data folder. For a defective update, switch channels or run a newer compatible Setup over the existing install; do not uninstall as a rollback mechanism. See [windows-updater.md](windows-updater.md).

Velopack's package SHA-256 verification detects corrupt/incomplete downloads and its staged update/fallback flow handles recoverable update failures. This is not a publisher signature: a compromised GitHub release could replace both the package and its checksum/feed. Setup.exe and the Godot executable are unsigned today. `vpk` supports Authenticode signing via `VPK_SIGN_PARAMS` (signtool parameter string), which is inherited by the package command without printing it. Issue #15 still needs an owner decision on legal publisher identity and certificate/service; supply signing credentials through a protected release environment/HSM or managed signing service before enabling it. No certificate was purchased, and this pipeline does not claim signatures are present. Godot's Windows Firewall prompt/elevation is not forced: the shipped game is an outbound WebSocket/EOS P2P client and contains no listener/server. No broad inbound executable rule is installed; a future direct-connection test may justify narrow Windows Firewall guidance. Offline and normal installation never request elevation. Bluetooth/ANT+ drivers remain optional device setup.

## Licensing and outstanding validation

`THIRD_PARTY_NOTICES.txt` and `ThirdPartyNotices/EOS/ThirdPartySoftwareNotice.txt` travel with the archive. OSM and LINZ-derived data attribution remains with the route bundles. The repository currently has no root `LICENSE`/`COPYING` file; select and add Wodra's intended source license before calling a public release open source. The Wodra license must not be applied to Epic's proprietary EOS DLL.

An extracted executable startup test and archive-content validation do not prove successful EOS authentication or multiplayer. Verify Online Riding and lobby creation using the alpha config on a separate Windows profile/device; each profile should generate its own EOS Device ID. Do not copy EOS identity caches. Current outstanding Phase 4 behavior: logs can show **EOS lobby joined · 2 riders · P2P connected** while the DEBUG view still says **Human Rider: waiting for state · visual none**, so the second cyclist and Catch Up offer are not yet reliable. This is a separate state-message flow issue and is not addressed by release packaging. Two-client rendering remains a release acceptance check.
