# Windows x64 alpha release

## Prerequisites

The release package job uses a dedicated Windows x64 runner because its build inputs include Epic's licensed EOS SDK 1.19.2.1 and the approved client configuration. Neither is committed to Git or available on a standard GitHub-hosted runner. The normal build/test validation does use `windows-2022`; only the package job requires the private runner. Install Godot **4.6.2 .NET** editor/export templates at `C:\Tools\Godot\Godot_v4.6.2-stable_mono_win64`, .NET SDK 10.0.204, licensed Visual Studio Build Tools with the x64 VC runtime redist, Git, and the EOS SDK at `%LOCALAPPDATA%\Wodra\EOS-SDK` (or set `EOS_SDK_ROOT`). Configure `%LOCALAPPDATA%\Wodra\eos-client.json` for that runner account using only the restricted Wodra Player client. The publisher checks the native EOS DLL, Epic's `ThirdPartyNotices` file, and the Visual C++ runtime files before building. The EOS DLL imports MSVCP140 and VCRUNTIME140/140_1, so the publisher includes those app-local dependencies and the matching Microsoft redistribution notice. Microsoft allows redistribution of unmodified redist files subject to Visual Studio license terms ([Microsoft redistribution guide](https://learn.microsoft.com/en-us/cpp/windows/redistributing-visual-cpp-files)). The EOS SDK and its Samples are never copied into the release.

Create `%LOCALAPPDATA%\Wodra\eos-client.json` from `eos-client.example.json` once, using only the restricted, user-required **Wodra Player** client policy. The zero-argument release command loads this config by default; `-EosClientConfigPath` can override its path. Client credentials are extractable from a distributed application. Do not use a trusted-server credential, and do not include identity caches. See [EOS Phase 4 setup](epic-online-services-phase4.md).

## Build and verify an alpha ZIP

From the repository root:

```powershell
dotnet build wodra.sln -c Debug -m:1
dotnet build wodra.sln -c Release -m:1
dotnet run --project tests/IndoorCycling.Physics.Tests -c Release
dotnet run --project tests/Wodra.Multiplayer.Protocol.Tests -c Release

.\publish.ps1
```

The alpha package version format is `MAJOR.MINOR.PATCH-alpha.N` (for example `0.1.0-alpha.1`); a matching GitHub tag is prefixed with `v`. The publisher derives a local alpha version from the latest tag and commit distance. Pass `-Version '0.1.0-alpha.1'` to set one explicitly. The final output defaults to `..\wodra_publish` (for this checkout, `C:\Users\garet\OneDrive\wodra_publish`). It contains `Wodra-windows-x64\`, the versioned portable ZIP and SHA-256 file, plus `Wodra-Velopack-<version>\` with Setup.exe, full/delta package when available, portable bundle, channel feed, asset manifest, release notes and an installer SHA-256 file. `-PublishRoot` overrides that final output directory. Builds, ZIP creation and smoke extraction use a unique staging directory under `%TEMP%`; only verified artifacts are copied into the output folder. Existing successful artifacts are backed up during replacement and restored if installation fails. The script does not delete unrelated files from the output folder.

The publisher serializes runs with a process mutex. It launches dotnet, Godot, and the extracted smoke test with separately captured output and errors, phase-specific logs, and timeouts; on timeout it terminates only the child process tree started by that invocation. Godot 4.6.2's managed export hook fails in this environment and has also stalled after saving the PCK. To avoid that unstable hook, the script exports a fresh PCK, stages the matching official Windows x64 .NET release template as the executable, and performs a fresh self-contained `dotnet publish` for managed files. It does not trust `.godot` cached outputs: it verifies the PCK, release template, fresh managed files, package ZIP, and extracted executable startup. `-SkipOfflineSmokeTest` skips that launch when a runtime environment cannot support it.

The expected routes are Oval to Gardens, South Dunedin Coastal, Rolling City and Valley, and Signal Hill Climbing. Each release carries route points/elevation, buildings, landmarks, street furniture, streets, terrain and vegetation sidecars. Their scenery is baked data, so neither the original OSM PBF nor LINZ rasters are needed on a player machine. The route verifier recomputes each geometry fingerprint and verifies any fingerprint stored in its route file.

The archive's EOS settings file is included from the default per-user config or from the explicit `-EosClientConfigPath` override. Configuration must remain outside the Git checkout. Its secret values are never printed by the packaging or verification steps.

The archive contains the Windows export, Godot's bundled .NET runtime and managed assemblies, EOS native runtime and its app-local Microsoft CRT dependencies, client config, route packages, and third-party notices. It does not contain the EOS SDK source/Samples, debug symbols, PDBs, route-authoring inputs, identity caches, local settings, FIT files, logs, or private user profile data. Epic documents the SDK package's `Samples`, `SDK`, and `ThirdPartyNotices` directories; only the native runtime and required notice file are included in Wodra's distribution ([EOS SDK download contents](https://dev.epicgames.com/docs/epic-online-services/eos-get-started/eos-get-started-reference)).

## GitHub Releases

`.github/workflows/windows-validation.yml` runs on protected-main pushes and pull requests. It uses a Windows 2022 runner, .NET SDK 10.0.204, and the pinned Godot 4.6.2 .NET editor/export templates. The solution is built with EOS disabled (so the workflow does not need Epic's proprietary SDK), and the available console regression suites run in Release. The Godot archive SHA-256 is checked before extraction.

`.github/workflows/windows-alpha-draft.yml` is a manual, tagged release path. It first calls the standard GitHub-hosted `windows-2022` validation workflow against the selected tag (Debug and Release builds, Godot headless launch, and regression suites). Only after that succeeds does it wait for the protected release Environment and package on the private runner. It validates that the existing `vMAJOR.MINOR.PATCH-alpha.N` tag is reachable from protected `origin/main`, then creates a **draft prerelease** through Velopack. Configure GitHub Environment `alpha-release` with a required maintainer reviewer and restrict deployment to `main`. Register one isolated Windows x64 self-hosted runner with labels `self-hosted`, `Windows`, `X64`, `wodra-release`; provision Godot 4.6.2 .NET/export templates, .NET SDK 10.0.204, licensed EOS SDK 1.19.2.1, Visual Studio Build Tools/VC redist, `%LOCALAPPDATA%\Wodra\eos-client.json`, and pinned `vpk` tool restore access for that runner's service account. Never register this runner for pull-request jobs or run fork code on it.

Workflow permissions are explicit: CI and the validation job get `contents: read`; only the protected draft-release job gets `contents: write` to create a GitHub draft and upload assets. `VPK_TOKEN` is set from that job's ephemeral `GITHUB_TOKEN`, so no PAT or repository secret is required. Approving the `alpha-release` Environment is the release authorization step. No signing secret is configured until the publisher identity/certificate decision for issue #15 is made. External contributions never receive release credentials or execute on the private runner.

After committing and reviewing code on `main`, create and push the version tag deliberately, then use **Actions → Prepare Windows alpha draft → Run workflow** on `main`, with that exact tag. The workflow creates a draft; a maintainer reviews the GitHub draft and publishes it as a prerelease as the final deliberate action. It does not create tags or publish releases automatically. Locally, `publish.ps1` still builds a non-publishing package to the existing default directory. Use `-CreateGitHubDraft -GitHubTag v0.1.0-alpha.1` only if intentionally creating a draft; the tag must already exist and point at the exact clean source commit.

The official Velopack Windows Setup installer uses a per-user install at `%LOCALAPPDATA%\Wodra` by default. It provides the stable launcher and `Update.exe` helper that Velopack updates through its normal lifecycle. Godot keeps the existing project name `Wodra`, so `user://` profiles, settings, ride history and other user data stay in Godot's user-data directory outside the installed application folder. Velopack uninstall removes the application and shortcuts; it does not include rider files stored in Godot's user-data path. Velopack update downloads are staged and checksum-verified by the framework; delta preparation failures fall back to the full package. Wodra only offers **Download and Install** from the startup screen, after rides are complete, with an explicit restart. Update checks and downloads can fail offline without blocking offline play, and the dialog offers Later and Retry.

The only public channel for alpha clients is `alpha`, and app assembly informational version, Velopack package version, and the `v`-prefixed tag must agree. The updater checks public GitHub Releases anonymously; no account/token is shipped. GitHub limits anonymous API requests to 60/hour/IP, so unusually large simultaneous update bursts may need a cache/static feed later. Release notes are generated from the latest commit subjects unless `-ReleaseNotesPath` is specified.

Velopack's package SHA-256 verification detects corrupt/incomplete downloads and its staged update/fallback flow handles recoverable update failures. This is not a publisher signature: a compromised GitHub release could replace both the package and its checksum/feed. Setup.exe and the Godot executable are unsigned today. `vpk` supports Authenticode signing via `VPK_SIGN_PARAMS` (signtool parameter string), which is inherited by the package command without printing it. Issue #15 still needs an owner decision on legal publisher identity and certificate/service; supply signing credentials through a protected release environment/HSM or managed signing service before enabling it. No certificate was purchased, and this pipeline does not claim signatures are present. Godot's Windows Firewall prompt/elevation is not forced: the shipped game is an outbound WebSocket/EOS P2P client and contains no listener/server. No broad inbound executable rule is installed; a future direct-connection test may justify narrow Windows Firewall guidance. Offline and normal installation never request elevation. Bluetooth/ANT+ drivers remain optional device setup.

## Licensing and outstanding validation

`THIRD_PARTY_NOTICES.txt` and `ThirdPartyNotices/EOS/ThirdPartySoftwareNotice.txt` travel with the archive. OSM and LINZ-derived data attribution remains with the route bundles. The repository currently has no root `LICENSE`/`COPYING` file; select and add Wodra's intended source license before calling a public release open source. The Wodra license must not be applied to Epic's proprietary EOS DLL.

An extracted executable startup test and archive-content validation do not prove successful EOS authentication or multiplayer. Verify Online Riding and lobby creation using the alpha config on a separate Windows profile/device; each profile should generate its own EOS Device ID. Do not copy EOS identity caches. Current outstanding Phase 4 behavior: logs can show **EOS lobby joined · 2 riders · P2P connected** while the DEBUG view still says **Human Rider: waiting for state · visual none**, so the second cyclist and Catch Up offer are not yet reliable. This is a separate state-message flow issue and is not addressed by release packaging. Two-client rendering remains a release acceptance check.
